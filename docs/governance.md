# 成员与治理插件

治理模块把资格输入、选民快照和匿名选票保存在 `plugins/mik/governance.db`。所有规则时间均按
UTC+8（`Asia/Singapore`）计算。

## 代码架构

此前按 `domain/application/adapter` 全局分层时，一次治理功能修改通常要同时进入三个大目录，
`GovernanceService`、仓储和命令控制器也持续聚集不相关职责。当前代码先按业务能力组织，再把 Paper
和 SQLite 放在外围：

```text
governance/
├── GovernanceModule.java              # 只负责创建、连接和关闭组件
├── membership/                        # 成员履历与选民资格
│   ├── MembershipService.java
│   ├── MembershipRepository.java
│   ├── profile/                       # 玩家治理档案
│   ├── participation/                 # 每日参与记录与窗口汇总
│   ├── promotion/                     # 晋升资格与晋升暂停
│   ├── activity/                      # 活跃成员资格
│   └── tenure/                        # 管理任期规则
├── voting/                            # 通用提案、选民快照、选票与结算
│   ├── VotingService.java
│   ├── VotingRepository.java
│   └── model/
├── removal/                           # 罢免联署及其开票条件
│   ├── RemovalService.java
│   ├── RemovalRepository.java
│   └── RemovalPolicy.java
├── delivery/                          # 结果公告与治理动作 Outbox
│   ├── DeliveryService.java
│   └── DeliveryRepository.java
├── platform/paper/
│   ├── command/                       # 命令树、分能力 handler 和展示文本
│   ├── membership/                    # 在线取样、自动晋升、任期检查
│   ├── delivery/                      # 公告和外部动作执行
│   └── role/                          # 唯一的 LuckPerms 治理角色网关
└── persistence/sqlite/
    ├── SqliteGovernanceRepository.java # 组合并实现四个窄仓储端口
    ├── SqliteGovernanceSchema*.java    # 结构声明、启动校验
    ├── SqliteGovernanceRows.java       # 行映射
    └── Sqlite*Store.java               # membership/voting/delivery 数据操作
```

能力之间的依赖方向为：`voting → membership` 获取冻结选民，`removal → membership + voting`
完成联署并原子开票，`delivery → voting.model` 保存待投递的投票结果。`membership` 不依赖其他治理
能力。`GovernanceAction` 表示外部副作用的可靠投递记录，因此归入 `delivery`，不再伪装成领域实体。

每个能力拥有自己的 Service 和 Repository 端口。业务代码不导入 Bukkit、LuckPerms 或 JDBC；
`platform` 不访问 SQLite，`persistence` 不访问 Paper。架构测试还限制装配根、命令路由和连接协调器
的文件规模，防止它们重新聚集业务实现。新增功能时，应先判断它修改的是成员资格、投票、罢免还是
投递规则，再进入对应能力；只有平台交互和 SQL 实现进入外围目录。

## LuckPerms 边界

命令、Axiom 和其他功能权限继续完全由现有 LuckPerms 组配置管理。MIK 不复制权限节点，也不对
新人建立命令黑名单；它只在状态发生变化时通过 LuckPerms API 增删 `member` 或 `moderator` 组并设置
主组。因此权限调整只需修改 LuckPerms 的组继承。

已有成员第一次被治理模块观察到时，LuckPerms 历史中没有“加入 member 组”的时间，因此首次建档
会以首次加入服务器时间作为 `member_since`；此后所有自动晋升均记录准确时间。

## 数据库边界

本插件尚未部署，数据库采用单一、干净的初始结构 v1，不包含升级、回填或旧结构兼容逻辑。首次启动
直接创建完整结构；若将来需要调整结构，应再单独设计显式迁移，而不是在启动时猜测旧表状态。

- 每次连接显式启用 SQLite 外键，并在启动时执行完整性、外键和治理快照一致性检查。
- UUID、枚举、时间范围、投票生命周期、晋升暂停书面字段等由 `CHECK`、外键和唯一索引共同约束。
- 开票后选民快照不可增删改；投票截止或终结后选票不可新增、修改或删除。
- 任命和罢免共享投票生命周期、冻结选民、匿名选票、计票、结算、公告与冷却逻辑。
  数据结构仍可读取和结算既有封禁投票，但不再提供发起封禁投票的命令。
- 罢免投票必须关联达到联署人数的罢免申请，建票、冻结选民与关联申请在同一事务提交。
- 通过投票与对应的通用治理动作在同一事务提交。动作队列支持 LuckPerms 任命、LuckPerms 罢免
  和既有封禁投票的 `BanManager` 动作；外部写入失败或服务器中断时，未完成动作会保留并重试。
- 投票结算与“结果已公告”状态分别持久化。结算后、公告前发生重启时，系统会在恢复后补发结果。
- 最后一名罢免联署人、罢免投票、冻结选民名单及申请关联在同一个事务内提交，任何一步失败都会
  整体回滚。

## 有效游玩与资格

- 每分钟取一次现有 AFK 模块的 `isActivityEligible` 结果，只累计连续两次取样均有效的在线时段。
- 单次取样最多累计 75 秒，服务器卡顿或暂停不会虚增在线时间。
- 跨 UTC+8 午夜的时段会拆到两个自然日。
- 新人晋升同时检查 3 天、8 小时、至少 2 个自然日、生效封禁和书面晋升暂停。
- 活跃成员按当日及此前 59/29 个自然日计算；累计时长包含所有有效秒数，只有单日达到
  30 分钟时才计为有效参与日。

## 游戏内菜单

打开 `/menu` 即可看到进行中的治理投票、本人选票状态和最近两项结果；有选民资格时，赞成、反对、弃权可直接在主菜单选择。多项议题用滚轮切换，读取与提交均走治理模块的单线程存储队列，提交时再次核验冻结选民名单和截止时间。从主菜单进入「治理」，或输入 `/gov`，可查看本人的身份与资格、完整议题详情及投票历史。符合资格的成员可在此报名管理或撤回；管理可辞任。罢免联署可在菜单中支持已有事项，或填写管理名字发起。管理与维护者还可通过「玩家管理」查看档案，并设置或解除新人晋升暂停。上述操作均在游戏内完成。

治理首页沿玩家正面的宽弧分区：个人身份与资格、进行中的议题列表在左侧，当前议题详情及赞成／反对／弃权按钮在正前方，最近结果与报名、联署、玩家管理等操作在右侧。选中的议题保持高亮，刷新与返回留在中央。历史页把列表、详情和操作分开；联署页把每页六项分到左右两列，说明与分页留在中央；玩家档案居中，管理动作在右侧。加载与失败页面也使用同一空间框架，并保留返回或重试入口。

菜单只调用现有治理服务与权限检查；投票仍按冻结的选民 UUID、法定人数和资格规则处理。弧面半径按实际文字与图标尺寸计算，各面板朝向玩家；布局不参与资格计算、存储或投票提交。空间画面使用玩家专属虚拟显示，不生成真实世界实体。

## 命令兼容入口

`/governance`、`/gov` 和 `/governance menu` 打开同一空间菜单；管理者输入 `/governance player` 可直接搜索玩家。以下子命令供控制台或熟悉命令的玩家使用：

- `/governance status`：以聊天文字查看自己的晋升或活跃成员资格。
- `/governance player <玩家>`：管理或维护者查看玩家履历、适用的资格条件及暂停信息。
- `/governance player <玩家> pause <期限> <申诉途径> <理由>`：暂停晋升；期限支持 `m`、`h`、`d`，需填写理由与申诉途径。
- `/governance player <玩家> resume <解除理由>`：解除生效中的晋升暂停并保留审计记录。
- `/governance nominate`、`/governance withdraw`：报名管理或撤回报名。
- `/governance list`、`/governance vote <编号> yes|no|abstain`：查看和参与匿名投票。
- `/governance show <编号>`：查看投票快照、当前参与数或最终分类票数；玩家只能看到自己的选择。
- `/governance history`：查看最近 10 次投票的完整汇总结果和终止原因。
- `/governance petitions`：查看正在征集共同发起人的罢免申请，只显示人数而不显示发起人名单。
- `/governance remove <管理>`：以活跃成员身份共同发起罢免；达到所需不同发起人数后自动开票。
- `/governance resign`：管理随时辞任。

任命和罢免投票均为三天，并使用相同的法定参与人数与通过门槛。正式封禁使用封禁模块的固定等级与
现行规则中的处理程序；已有的封禁投票记录仍可查询，待执行动作仍会完成。

开票时会把合资格 UUID 写入不可变选民名册，同时固定选民数和法定参与人数。投票中只公开参与数，
不公开实时赞成、反对或弃权分项；每名玩家可以私下确认自己的当前选择。截止后公布选民总数、参与
数和赞成/反对/弃权汇总，不提供查询他人选择的命令。候选人在截止前失去活跃成员资格或主动撤回时，
任命投票会记录具体原因并自动终止。未达到法定参与人数的投票在三天内不能重新发起。

## 每日管理状态

系统按 UTC+8 午夜检查 LuckPerms 的 `moderator` 组和 Paper 的成功登录记录。超过 180 天未登录者按
离线时间由长到短卸任，但本流程最多卸任到剩余四名；辞任和投票罢免不受此下限约束。`custodian`
组不参与管理任免或离线卸任，仍可依规则行使管理权限。

## 运维注意

“每个自然人的指定账号”需要可信的自然人到账户映射。现有 Minecraft UUID、IP 关联和外部平台绑定
都不足以单独证明两个账号属于同一自然人，因此模块当前冻结并去重的是 UUID。上线治理投票前，应由
身份系统提供该映射；不能使用 IP 自动合并账号，因为共享网络会错误剥夺选举权。
