# 设计准则

适用于产品、游戏、工具的界面、内容、实现与验证。

## UX：任务与界面

**信息按需呈现。** 只展示当前任务需要的信息，详情与低频设置按需查询。常驻内容必须持续影响当前判断，任务结束后收起，重复提醒合并。

```
正例：比赛时显示比分和剩余时间，结束后收起。
反例：日常游玩时常驻服务器介绍和命令大全。
```

**操作与反馈一致。** 控件说明动作与状态，禁用项说明原因。操作后直接更新对应界面，耗时任务显示真实阶段或进度，失败提供恢复方式。

```
正例：「切换到手动挡」执行后，按钮状态与读数立即更新。
反例：按钮只写「操作」，点击后仅在聊天框显示「成功」。
```

**确认与代价匹配。** 低成本、可逆操作直接执行；高代价或不可逆操作确认对象与后果，取消或失败保留已有输入。

```
正例：开关 HUD 直接生效；删除模型前确认模型名称与后果。
反例：每次开关 HUD 都确认，删除模型却直接执行。
```

**视觉表达语义与主次。** 灵活运用颜色、字号、间距与位置，突出关键句及句内重点，弱化辅助信息，同类语义保持一致。文字按实际内容布局、保持清晰对比，状态同时用文字或图形表达。

提示按内容灵活选择明亮配色；正文、辅助文字和分隔符都须清晰可读，不使用灰色、深灰、黑色等低可读性颜色。

```
正例：<yellow>附近有 <gold>2</gold> 名玩家处于 <gold>隐身</gold> 状态</yellow> <white>· 最近约 12 格</white>
反例：<red>附近有 2 名玩家处于隐身状态 · 最近约 12 格</red>
```

## 内容：文案、文档与翻译

**每句话提供有效信息。** 按读者需要写清用途、条件、结果与下一步，保留限制、风险和设计依据。删除铺垫、客套、重复结论、自我评价及无关否定，可操作的提示直接提供入口。

日常与情境 tip 只保留核心用途和关键操作，按[提示文案规范](guidance.md#文案与呈现)突出重点；详细条件和排查步骤放在功能说明中。

```
正例：退出服务器会丢弃未保存草稿，请先保存。
反例：这不是旧版草稿方案，也不是其他方案，未来将持续完善。
```

**由目标语言组织完整表达。** 传入语义与原始数值，由语言资源安排语序及复数、格、人称配合，同一消息内部处理数量变化，术语保持一致。

```
正例：1 nearby player is invisible / 2 nearby players are invisible
反例：1 nearby player(s) are invisible
```

## 工程：职责与维护

**按所有权组织功能。** 依据规则、数据和生命周期确定归属，跨功能通过明确能力连接。

```
正例：载具专用适配随载具维护，共用菜单机制集中管理。
反例：所有页面放进全局 ui，所有业务逻辑放进 util。
```

**同一规则或事实维护一处。** 同一业务规则、文档事实或共性检查只维护一处，其他入口引用或复用，抽象依据实际需求建立。

```
正例：地段命令与菜单共用鉴权，权限目录由一份手册维护。
反例：各入口另写鉴权，多份文档各复制一份权限表。
```

**改动与清理一起完成。** 同步受影响的入口、权限、存储、翻译、测试与文档，删除旧别名和失效代码。

```
正例：合并数量消息时同步全部语言和调用方，删除 single、multi 旧键。
反例：新旧名称长期并存，旧键继续转发到新键。
```

## 验证：行为与性能

**测试防住具体错误。** 通过真实输入验证可观察结果和关键边界，简单转发由上层行为覆盖，只保留能识别具体缺陷的测试。

```
正例：向模组检测器传入截断注册包，验证无异常且无部分误判。
反例：只断言 mock 返回预先设定的模组列表。
```
