# 场景提示

各功能声明自己的提示和适用条件：情境提示连接类型化事件源，日常随机提示加入共享提示池。提示服务按需注册 Bukkit/Paper 事件，统一处理随机调度、主线程提交、频率控制、多语言展示和历史记录；业务状态与判断仍由所属功能维护。

## 已接入的场景

| 场景 | 触发与复核 | 基础间隔 |
| --- | --- | --- |
| 客户端版本 | 入服事件确认后，已知 Java 客户端协议早于服务器时建议检查更新 | 7 天 |
| 推荐模组 | 与版本建议同组，发送前读取当前连接的安装信号，提供模组名称和下载链接 | 7 天 |
| 创建家园 | 聊天明确提及家园、设家或 home 命令；改变方块或世界的传送另有 10% 概率提交。须当前没有 home 且未打开家园菜单 | 1 天 |
| 家园返回 | 首次创建家园成功后，家园仍有效且未处于家园菜单时介绍 `/home` | 30 天 |
| 返回位置 | 改变方块或世界的传送后有 10% 概率介绍 `/back`；须有可返回位置且不在返回传送途中 | 1 天 |
| 撤销返回 | 同一次传送独立按 10% 概率介绍 `/reback`，与返回位置同组；不把尚无撤销记录描述为已有记录 | 1 天 |
| 铁块电梯 | 参与日常随机池，无需发生操作或靠近电梯 | 1 天 |
| 玩家对战 | 双方均为生存或冒险、都未开启 PVP 时向主动攻击者介绍 `/pvp`，发送前复核；强制 PVP 规则生效时跳过 | 1 天 |
| 返回主城 | 日常随机，或聊天提及出生点、主城、回城、大厅、独立的 `spawn`、`lobby` 及对应命令；须主城世界可用 | 1 天 |
| 物品帽子 | 日常随机，或聊天提及帽子、头饰、戴到头上、穿到头上等说法，以及独立的 `hat`、`hats`、`headwear`、`/hat` | 1 天 |
| 清理掉落物 | 日常随机，或聊天提及掉落物、地上物品、`dropped items`、`item drops` 及清理命令；须有 `mik.command.removeitems` 权限 | 1 天 |
| 名称标签 | 仅日常随机，介绍 `/nametag`；复用 `RolePermissions.isMember` 检查 | 1 天 |
| 性能信息栏 | 日常随机，或聊天提及 `tps`、`mspt`；须有 `mik.tpsbar` 权限 | 1 天 |
| 私聊频道 | 在公共频道累计成功使用两次 `/msg 玩家 消息`，介绍 `/msg 玩家` 切换私聊频道、`/public` 返回公共频道；发送前仍须处于公共频道 | 1 天 |

表内基础间隔用于日常与普通事件的递增提醒；聊天使用下述自适应概率。所有入口共用最近展示时间和全局频率限制。
客户端检测的依据与限制见[客户端提醒](client-reminders.md)。客户端建议、设家提醒和随机返回提示按当前情况判断；点击下载链接不会被当作安装成功。

各模块声明自己的关键词表达式，共用 `TipTriggers.chatMentions(pattern)`，在聊天线程匹配可见文本并排除链接，下一主线程时刻核对连接、取消状态并提交候选，发送前再读取业务状态。Home 只匹配家园、设家、回家等明确中文词语，以及独立的 `home`、`homes`、`sethome` 或对应命令；`homework`、`homepage` 不触发。主城提示忽略 `spawner`、`respawn`、`lobbyist`，帽子提示忽略 `that`、`chat`、`hatchet` 等无关词。模块无需自行维护监听器或切线程任务。

掉落物提示和清理命令共用权限节点，权限只在主线程读取，发送时按最新权限决定是否展示。`/rmitems` 是现有清理命令入口，可省略半径以使用默认 50 格，也可指定 1～300 格；提示只保留核心用途和可选参数，点击填入命令，不执行清理。

性能信息栏匹配不区分大小写，支持 `TPS多少`、`MSPT太高`、`20tps` 等中文及数值相邻的说法；链接及英文单词内的片段不参与匹配。命令、入服恢复与提示共用 `mik.tpsbar` 权限节点。

私信命令的 `/tell`、`/w`、`/whisper` 别名共用 `/msg` 的发送入口，累计次数不区分接收者。无效目标、自发私信、切换频道和其他频道内的私信不计入；启用延迟时只在实际发送成功后计入，取消或目标离线不计入。达到两次后仍遵守提示的递增间隔，不永久禁用，也不加入日常随机池。

PVP 在自己的伤害保护判定处提交 `offer(attacker, victimId)`，被本功能阻止的攻击仍能产生提示，不依赖通用事件源接收已取消事件。近战及可归因于玩家的间接攻击共用判断；提示只保留对方 UUID，发送时重新读取在线玩家、游戏模式与有效 PVP 状态。冷却和历史仍由提示服务管理。

## 调度与存储

### 及时投递

情境提示默认不设主动延迟。异步聊天、传送等原生事件先在下一主线程时刻复核取消状态
和操作结果；抽中候选后，所有受影响玩家共用一个下一主线程投递任务，同一玩家在这
期间收到的候选一起选择、合并。家园保存、私信发送、PVP 拦截等手动来源也走同一入口。
候选不等待每秒维护轮询，也不为凑齐同组建议多等 1 秒。

需要异步结果的业务应在成功回调、状态写入完成后调用 `offer`，不靠固定等待几秒猜测
操作已经完成。投递前仍复核当前状态和权限。AFK、死亡、全局间隔等阻止展示时，已就绪
的情境候选直接丢弃，避免恢复后才出现过时提示；未展示不消耗展示档位。

每秒任务继续负责日常随机机会、显式延迟候选的到期检查，以及有变化的 PDC 记录。
退出会清理该连接待投递的请求，停用会取消共享投递任务。

### 新人加成

主线程按当前 `group.member` 权限判断：没有该权限的玩家获得 2 倍提示加成，不另行缓存
或持久化新人标记；其他身份权限不替代这项判断。

- 聊天自适应抽签、普通事件与手动概率提交，均在算出最终抽签概率后乘以 2，最高 100%；
  原概率为 0 的来源继续关闭，原本必中的来源仍为必定入选。
- 日常随机机会的等待时间减半，从 15～30 分钟缩短为 7.5～15 分钟；每次仍只选一条。
  等待中的机会也按最新权限重新计算到期时间。
- 各提示的功能权限、业务条件、重复提醒间隔、AFK/死亡限制和全局 45 秒间隔继续生效。
  匹配密度与展示历史仍按玩家和场景独立保存，权限变化不清空历史。

### 聊天概率

`TipTriggers.chatMentions(pattern)` 自带自适应抽签，模块只提供关键词。对通过主线程业务条件和权限检查的匹配，计算：

```text
d = 上次密度 × 2^(-距上次匹配的时间 / 30 分钟)
r = min(1, 距上次实际展示的时间 / 1 小时)；从未展示时为 1
p = r / (1 + d)²
最终概率 = min(1, p × 加成倍数)；新人为 2，拥有 group.member 为 1
```

- 初次有效匹配为 100%；同一条消息包含多个关键词仍只计一次。
- 每次有效匹配后更新密度为 `min(32, d + 匹配条数)`，记录匹配时间。未抽中、等待发送或受全局间隔限制时也保留匹配密度；不提前更新展示记录。
- 同一主线程分发前的连续消息只保留最新上下文和有上限的条数，进行一次抽签，计入整个批次的密度。初次或密度已归零的批次仍为 100%；存在近期压力时，当前批次额外消息也计入抽签密度，最高为 32。
- 密度小于 `1/256` 时按 0 处理。停止匹配足够久后概率恢复到 100%，不永久禁用提示。密度只在机会到来时计算，无周期性衰减任务。
- 聊天来源不设主动延迟，主线程确认并抽中后立即就绪，加入下一主线程投递批次；同场景已有较慢来源的候选也会提前就绪。
- 聊天不受日常提醒的多天间隔阻断，但仍遵守全局 45 秒间隔、权限、业务条件和有效期。100% 表示通过抽签，不能绕过这些条件。

例如距上次实际展示至少 1 小时，当前衰减密度为 1、5、10 时，概率分别约为 25%、2.8%、0.83%。长时间后密度归零，恢复为 100%。

### 有限的重复间隔

普通事件、手动提交和日常抽选使用基础间隔乘以展示档位：`1、2、4、8、16、32`，最长为 `max(基础间隔, 30 天)`。默认基础间隔为 1 天，对应 `1、2、4、8、16、30` 天。只有实际展示才推进档位；聊天的实际展示也更新同一份记录。情况键变化时从初始档位重新计算，一年以上没有展示的场景重新从首档开始。

日常机会按玩家独立等待随机 15～30 分钟，新人减半为 7.5～15 分钟，从当前适用且已到提醒时间的场景中等概率选一条，不到期立即推送。AFK、死亡、全局间隔及等待中的情境候选会跳过本次机会，不积压补发。

### 玩家记录

每名玩家的数据保存在自己的 `mik:tip_history` PDC 子容器中，随玩家数据持久化，由 Paper 管理保存生命周期，见 [Paper PDC 文档](https://docs.papermc.io/paper/dev/pdc/)。不建立全服玩家档案或独立写盘线程。

每条场景只保存四个数：最近匹配时间、密度、最近实际展示时间、展示档位，编码为一个 `LONG_ARRAY`。密度按 `1/256` 定点精度存储；固定数组占 32 字节，不含场景键和容器开销。静态场景直接复用场景 ID，只有动态情况另存字符串。全局最近展示时间从这些记录推导，不重复存储；不保存译文、组件、完整事件或逐次日志。

入服按玩家读取，运行时只缓存在线玩家；离线前把改变的记录写回 PDC，再释放缓存。共享的每秒调度只对有变化的玩家更新 PDC，插件停用时补写剩余变化。无匹配且无展示超过一年的记录在加载时排除，下次有变化写回时清除；无效单条记录不影响其他场景。全部 PDC 操作在主线程完成，不强制触发玩家文件保存。

### 候选与事件

- 每名玩家最多保留 8 个候选；同一场景刷新上下文但不推迟发送或延长有效期。过期后重新计时。
- 每种 Bukkit/Paper 事件只注册一个原生监听；按当前连接合并主线程分发。先验证取消状态及操作结果，再按最高基础概率选每场景的一个来源，同概率取最新来源。
- 传送须改变方块或世界，并在主线程确认已到达最终目标；仍按所属模块声明的固定概率抽签。抽签未命中不替换已有候选。
- 先复核业务条件与提醒间隔，再由优先级最高的有效候选决定分组；只合并本批次已就绪的同组候选，最多 3 条，不等待尚未就绪的来源。其他到期候选丢弃。
- AFK、死亡时丢弃已就绪候选，仍淘汰过期候选；退出、作用域关闭和插件停用清理相应队列与任务。来源异常不阻断其他来源。
- 时间回拨不使用未来时间阻断提示；只有实际发送才更新展示时间和档位。

## 多语言

提示标签与正文复用[共享语言服务和 Fluent 资源](localization.md)，已接入场景均提供全部 16 种语言的译文。语言选择沿用个人设置、客户端语言和地址推断的现有规则。

发送前统一读取玩家当前语言，一批合并提示的标签与正文使用同一语言。事件分发与投递之间切换语言，最终发送使用新语言。文案渲染失败时跳过该条，其他有效来源仍可参与分组，失败项不写入展示历史。

普通提示用 `define(id, Message)` 声明，服务在发送前解析本地化 MiniMessage，未指定颜色时回退为白色，保留模块自行声明的配色。消息以 `-mm` 命名，可在资源中声明重点颜色、命令点击、原版翻译名和物品悬浮框；模块无需编写额外渲染逻辑。带动态参数的提示使用内容回调和模块已有的语言服务。场景 ID 与情况标识独立于语言，翻译后的文本和语言代码不参与调度记录。

## 文案与呈现

提示遵循[设计准则](design-principles.md)：只保留当前需要的用途与关键操作，详情留在功能说明中。

- 句子短、直接，不展开边界条件、安装排查或重复的“点击填入命令”。
- 按场景与语义灵活配色，用明亮、易读的颜色区分正文、动作、对象与状态。控制重点数量，保持清楚的主次。
- 正文、辅助文字和分隔符均不用灰色、深灰、黑色等低可读性颜色。可点击内容保留下划线等明确交互线索，颜色由所属功能选择。
- 命令点击填入对应命令，不自动执行。多个命令分别绑定各自操作，不能点击 `/home` 却填入 `/sethome`。
- 原版物品使用客户端翻译名和原生 `show_item` 悬浮框，不手写名称或模拟物品说明。铁块通过本功能的 FTL 术语复用 `<lang:block.minecraft.iron_block>` 和物品 ID；名称由客户端语言资源显示。
- 动态内容保持字面值：富文本参数通过 `RichArg` 插入；需要 MiniMessage 的字符串参数先转义，不把版本名等数据作为标记解析。

各场景按内容安排层次与配色。静态文案的颜色和交互保留在各功能的 Fluent 资源中；动态模组链接由所属功能构建组件，调度服务只负责选择语言与发送。

## 功能接入

公共能力位于 `feature/player/guidance/`。场景定义与适用条件留在功能所属目录：当前客户端场景在 `feature/player/client/tip/`，家园与返回场景在 `feature/player/teleport/`，玩家对战场景在 `feature/player/pvp/`，名称标签场景在 `feature/player/profile/`，主城、帽子与掉落物清理命令及其提示在 `feature/player/utility/`，性能信息栏场景在 `feature/server/performance/`，铁块电梯场景在 `feature/world/elevator/`，私聊场景在 `feature/community/chat/ChatTips.java`。

接入模块只声明触发方式、文案和简单的适用条件。条件直接查询已有业务状态，例如 home 列表、返回位置或客户端检测信号。匹配密度、展示间隔和候选队列均由提示服务维护，历史统一保存到玩家 PDC；加载、更新和退出清理由服务完成。模块重新创建时只需按相同 ID 重新声明场景，服务继续使用已有记录。

普通自动提示只需构造时声明一次。需要在业务成功后触发时，保留一个 `Tip` 句柄并调用 `offer`。事件快照是一次触发的临时数据。Home 的家园存档、Back 的返回历史和客户端的连接信号属于原功能的业务数据，提示条件直接复用这些事实。

业务侧可先组合自己的筛选和状态，再调用普通 `offer`，不把场景专用规则扩入通用策略或展示历史。`ChatTips` 把公共频道检查、私信发送成功回调与累计次数组合成一个 `Consumer<Player>`；次数在聊天自己的 PDC 键中以一个字节保存，累计到 2 后不再写入。该状态随玩家保存，无额外缓存、写盘或退出清理；提示的 `when` 只负责发送前再次检查当前频道，不在渲染期间累计次数。

[客户端检测](client-reminders.md#能力与归属)由 `client/detection/` 独立维护，`ClientTips` 只读取 `ClientVersions`、`ClientMods` 的快照。推荐清单、下载链接和提示文案留在 `client/tip/`，检测器只负责协议事实。

Home 的创建提示如下：

```java
tips.define("home-create", Message.HOME_TIP_CREATE_MM)
        .group("home").priority(90)
        .when(player -> getHomeNames(player).isEmpty() && homeScreen.flow(player).isEmpty())
        .on(TipTriggers.chatMentions(HOME_MENTION))
        .on(TipTriggers.teleport(0.1))
        .suggestCommand("/sethome ")
        .build();
```

`Tip<C>` 描述给玩家的建议及当前是否适用；`TipTrigger<E>` 描述从哪个事件取得接收者、如何筛选事件及触发概率。统一通过 `on(trigger)` 连接，两者分别使用业务上下文类型和原生事件类型。纯自动场景无需保存返回的 `Tip`，也无需编写监听器、内容包装或关闭代码；点击填入命令用 `suggestCommand`。

## 日常随机提示

没有特定操作前提的功能介绍使用 `.ambient()`。铁块电梯模块只需声明：

```java
tips.define("iron-elevator", Message.IRON_ELEVATOR_TIP_MM).ambient().build();
```

`/nametag` 的介绍同样只使用 `.ambient()`，通过 `.when(RolePermissions::isMember)` 复用命令权限，不注册聊天或其他事件源。

无需事件源、监听器、手动 `offer`、计时器或额外玩家数据。可以叠加 `.when(player -> ...)` 查询已有业务状态，或调整 `.interval(...)`；它们与情境提示共用条件、情况标识、展示档位和持久化历史。同一场景也可同时声明事件源或手动提交，所有入口共用展示记录。

`.ambient()` 只加入共享日常池，服务负责间隔、随机选择和让位于情境提示；单次直接读取当前状态并发送，因此 `.delay(...)`、`.lifetime(...)`、`.group(...)` 与 `.priority(...)` 只控制事件和手动提交的候选。日常求值没有事件数据，上下文为 `null`。未声明 `.ambient()` 的手动场景不会自行随机展示。

退出清除本次连接的随机时间，保留展示历史；作用域关闭时移除其日常声明。随机间隔属于共享投递策略，模块无需为每条介绍选择计时事件或重复注册周期任务。

## 接入其他事件

`TipTrigger.event(PlayerJoinEvent.class)` 等 `PlayerEvent` 来源默认以事件的玩家为接收者。方块、实体、背包等事件通过另一个重载明确指定接收者，例如：

```java
TipTrigger<BlockBreakEvent> mining = TipTrigger.event(BlockBreakEvent.class, BlockBreakEvent::getPlayer)
        .filter(event -> event.getBlock().getType() == Material.DIAMOND_ORE)
        .chance(0.1);
```

模块将它传入 `.on(mining)` 即可。接收者提取函数返回 `null` 时忽略该次事件；自定义插件事件也可使用相同入口，只需满足原生事件的注册要求。注册遵循 [Paper 的事件监听约定](https://docs.papermc.io/paper/dev/event-listeners/)，统一使用 `MONITOR` 观察事件、忽略已取消的事件，并在主线程提交前再次检查取消状态。

各阶段的职责与线程保持明确：

| 入口 | 执行时机 | 用途 |
| --- | --- | --- |
| 接收者提取、`filter(event)` | 原生事件线程 | 选择接收者、筛选事件；异步事件只读取自身携带的数据 |
| `on(trigger, event -> context)` | 原生事件线程，匹配后立即执行 | 提取业务标识或不可变快照，避免背包、物品等状态随后变化 |
| `verify(event)` | 下一主线程时刻 | 可选的操作结果确认，例如传送后确实到达目标 |
| `when(player)`、`when(player, context)` | 自适应来源入队前及所有来源发送前 | 在主线程读取最新状态与权限；无效匹配不增加密度，发送时再次复核 |

条件可多次声明，须全部满足。异步来源的筛选、接收者提取和快照回调不得读取实时 Bukkit 状态；需要这种检查时使用 `verify` 或 `when`。提示等待期间只保留上下文，不保留原生 `Event`；原生事件仅用于到下一主线程时刻的取消与结果复核。上下文应保存 ID、枚举或复制后的数据。

例如消费物品时，可以用 `.on(TipTrigger.event(PlayerItemConsumeEvent.class), event -> event.getItem().getType())` 为 `Tip<Material>` 提取物品类型，发送前的条件和内容回调都收到同一份类型化数据。

事件源是不可变声明，`filter`、`verify` 和 `chance` 返回新声明，可跨提示复用。`TipTriggers.teleport(chance)` 封装 Home 与 Back 共用的“跨方块或世界且已到达”判断，`chatMentions(pattern)` 复用聊天可见文本匹配、链接排除与自适应概率；其他事件可按实际需要声明 `.adaptiveChance()`。普通事件仍直接使用 `TipTrigger.event(...)`。新增事件只需模块声明其类型与接收者。

底层每种事件类型只注册一个原生监听，按类型分发给已订阅的提示。某个作用域关闭时只移除它的订阅；最后一个订阅关闭时注销该类型的监听。每个连接至多一个主线程任务，事件源在该任务内各占一个槽位，频繁重复事件不会持续累积任务或事件实例。

## 提示策略与业务事件

默认分组为场景 ID，优先级为 0，基础间隔为 1 天，主动延迟为 0，有效期为 20 秒。
只有业务存在明确的未来展示时间时才显式配置 `.delay(...)`，异步操作应优先使用完成
回调提交候选；客户端版本和模组建议也不再统一等待 10 秒。聊天关键词来源始终默认零
延迟，即使同场景其他来源显式设置等待时间也不受影响。无效配置和重复 ID 在注册时报
告，基础概率必须是有限的 `0..1` 数值；`0` 不触发，自适应来源将基础概率与计算结果相
乘。聊天入口已采用基础概率 `1`，模块无需另配概率。

模块自身的业务事件需要携带数据时，保留一个带类型的句柄。例如，第一次保存家园后介绍如何返回：

```java
returnTip = tips.<String>define("home-return", Message.HOME_TIP_RETURN_MM)
        .group("home").priority(80).interval(Duration.ofDays(30))
        .when((player, name) -> homeScreen.flow(player).isEmpty() && getHome(player, name) != null)
        .suggestCommand("/home")
        .build();

// 家园保存成功后提交事件数据。
returnTip.offer(player, homeName);
```

`Tip<C>` 只需接收玩家和类型化数据；没有事件数据时可用 `Tip<Void>` 与 `offer(player)`。自动来源使用 `on(trigger, contextMapper)` 携带事件快照，单参数 `on(trigger)` 的上下文为 `null`。业务自身完成保存、网络响应等操作后也可手动调用 `offer`；需要概率时使用 `offerRandomly(player, context, chance)`，无数据时省略 `context`。所有入口共用场景、展示历史和生命周期。

只有文案含动态参数、富文本或不同建议对象时才需要 `resolve`。它接收当前在线玩家、事件数据与发送端选定的 `Language`，返回 `Optional<TipContent>`；返回空值表示当前场景不适用。例如客户端版本提示：

```java
tips.<Void>define("client-version")
        .group("client-setup").interval(Duration.ofDays(7))
        .lifetime(Duration.ofSeconds(45))
        .on(TipTrigger.event(PlayerJoinEvent.class))
        .resolve((player, ignored, language) -> versions.version(player)
                .filter(ClientVersions.Version::outdated)
                .map(version -> versionAdvice(languages, language, version)))
        .build();
```

内容回调使用传入语言和模块已有的 `LanguageService` 调用 `text`、`format` 或 `rich`；`TextArg` 和 `RichArg` 保留 Fluent 的数值选择与 Adventure 的样式和事件。`TipContent` 只保存稳定的情况标识和本地化组件。普通消息默认以场景 ID 为情况标识；动态建议则使用客户端与服务器版本组合、推荐模组清单等稳定标识。不要使用每次登录的随机数，也不要因玩家完成部分安装而改变清单标识。每个场景仅保存最近一次情况。

事件数据应保存业务标识或快照，文案在发送前生成。条件和内容回调应只读，不执行文件、网络或耗时计算。取消当前候选用 `tip.cancel(playerId)`。

作用域由 `bootstrap` 创建并托管，再通过构造函数注入：

```java
HomeModule home = new HomeModule(plugin, language,
        lifecycle.own("home-tips", tipModule.scope()));
lifecycle.startManaged("home", home::enable, home::disable);
```

模块无需保存或关闭作用域。逆序停用先关闭模块，再关闭其提示作用域，最后关闭提示服务；构造或启动失败也会回收已托管的作用域。作用域关闭统一移除自动订阅、待执行任务和候选，不影响其他功能，旧句柄停止发布。

实现按职责保持在同一功能包内：`Tip` 与 `TipScope` 提供提示声明和操作能力；`TipTrigger` 声明类型化事件源，`TipTriggers` 保存已共用的事件语义；`TipEvents` 管理原生订阅及主线程转发；`TipDeliveryQueue` 合并下一主线程投递任务；`TipScheduler` 管理有界候选、合并与日常随机池；`TipState`、`TipStore` 管理历史与存储；`TipModule` 连接 Paper、语言与玩家 PDC 生命周期。事件适配器不导入 Home、Back、客户端或电梯模块。

其他插件、原版玩法或客户端设置也能使用同一能力：由了解它们的功能或适配提交候选。服务不需要导入这些功能、协议或 API；不了解当前状态时，可以提供准确的说明入口，不能把未知状态断言为缺失或故障。
